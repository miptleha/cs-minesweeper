# 05 — Roadmap

План развития проекта **`cs-minesweeper`** по этапам.

> **Текущее состояние:** решение и проекты созданы, но **пусты**. Никакой игровой логики, UI, тестов и инфраструктуры ещё нет. Этот документ описывает, как двигаться от пустого решения к работающей игре с несколькими UI.

Документ **живой**: по мере прохождения этапов отмечайте выполненные пункты и уточняйте формулировки. Если план расходится с реальностью — обновляйте план, а не подгоняйте реальность под план.

---

## Принципы движения по этапам

1. **Один этап — один работающий результат.** Не начинать следующий этап, пока текущий не даёт запускаемое приложение (или проходящие тесты).
2. **Core — первым.** Ни один UI не пишется, пока в Core нет минимально достаточного API. Исключение: UI-заглушка для проверки, что проект вообще собирается.
3. **Правила — из `02-GAME-RULES.md`.** Не «додумывать» поведение в коде. Если правила не описывают ситуацию — сначала обновить правила, потом код.
4. **Тесты — вместе с логикой, а не «потом».** Каждое правило из раздела 6–9 `GAME_RULES.md` должно иметь тест.
5. **Каждый этап заканчивается обновлением документации**, если реальность разошлась с описанием.

## Этап 1 — Core: домен и генерация поля

**Цель:** в Core есть модели и корректная генерация поля с гарантией безопасного первого хода. UI ещё не подключён.

**Статус:** ⬜ не начат

### Задачи — Domain

- [ ] `Point` (`readonly record struct Point(int X, int Y)`).
- [ ] `CellState` — enum: `Closed`, `Open`, `Flagged`.
- [ ] `CellContent` — enum: `Empty`, `Number`, `Mine` (или `CellContent` как `record struct` с `int NeighborMines` — решить до реализации; зафиксировать в `03-ARCHITECTURE.md`).
- [ ] `Cell` — иммутабельный снимок (`readonly record struct` или `sealed record`), без публичных сеттеров.
- [ ] `Board` — размеры + доступ к клеткам; без логики открытия.
- [ ] `GameSettings` — `record` с `Width`, `Height`, `MineCount`, `DifficultyLevel`.
- [ ] `DifficultyLevel` — enum: `Beginner`, `Intermediate`, `Expert`, `Custom`.
- [ ] `DifficultyPresets` — статические настройки трёх уровней из `02-GAME-RULES.md` (9×9/10, 16×16/40, 30×16/99).
- [ ] `GameState` — enum: `NotStarted`, `InProgress`, `Won`, `Lost`.

### Задачи — Abstractions

- [ ] `IRandomProvider` с методом `int Next(int maxExclusive)`.
- [ ] `SystemRandomProvider` — реализация в Core (обёртка над `Random`).
- [ ] `TimeProvider` — использовать встроенный из .NET 8, без своей абстракции.

### Задачи — Engine: генерация мин

- [ ] `MinePlacement` — размещение `MineCount` мин на поле.
- [ ] **Ленивое размещение** (по `03-ARCHITECTURE.md`, раздел 5.2): мины не размещаются в конструкторе; размещаются при первом `OpenCell`, так чтобы открываемая клетка была безопасной.
- [ ] Валидация `GameSettings`: `0 ≤ MineCount ≤ (Width−1)×(Height−1)`, `Width ≥ 9`, `Height ≥ 9`, `Width ≤ 30`, `Height ≤ 24` (для Custom; для пресетов — фиксированные значения).
- [ ] Подсчёт `NeighborMines` для каждой клетки после размещения.

### Задачи — тесты

- [ ] `MinePlacementTests`:
  - [ ] Размещает ровно `MineCount` мин.
  - [ ] Не размещает мины в первой открываемой клетке (при детерминированном `IRandomProvider`).
  - [ ] Корректно считает `NeighborMines` для углов, краёв и центра.
- [ ] `GameSettingsTests`: валидация границ (негативные сценарии).
- [ ] `DifficultyPresetsTests`: три пресета соответствуют правилам.

### Критерий готовности этапа

- [ ] Все тесты из этого этапа проходят.
- [ ] `dotnet build` без warnings в Core.
- [ ] Архитектурный тест (reflection) подтверждает, что Core не ссылается на UI-сборки.
- [ ] В `03-ARCHITECTURE.md` при необходимости уточнена форма `CellContent` (enum vs record struct).

### Риски и заметки

- **Ленивое размещение vs перемещение мины.** Правила (`02-GAME-RULES.md`, раздел 5) описывают поведение «переместить мину из-под первого клика». Ленивое размещение даёт тот же наблюдаемый результат, но проще в тестах. Убедиться, что это согласовано с документом правил (там про реализацию — сноска).
- **`CellContent` как enum vs struct.** Enum проще, но не хранит `NeighborMines`. Struct удобнее для UI. Решение зафиксировать в архитектуре, чтобы все UI работали одинаково.

## Этап 2 — Core: игровой движок и события

**Цель:** `GameEngine` полностью реализует правила игры и поднимает события. Core можно использовать из тестов-«потребителей», даже если UI ещё нет.

**Статус:** ⬜ не начат

### Задачи — Engine

- [ ] `GameEngine` с публичным API из `03-ARCHITECTURE.md`, раздел 5.
- [ ] `OpenCell(x, y)`:
  - [ ] Первый вызов — ленивое размещение мин, безопасная клетка.
  - [ ] Открытие клетки с `N > 0` — открыть одну клетку.
  - [ ] Открытие клетки с `N = 0` — каскад через `RevealService`.
  - [ ] Открытие мины — `GameState.Lost`, открыть все мины.
  - [ ] Открытие уже открытой клетки — no-op.
  - [ ] Открытие клетки с флагом — no-op.
- [ ] `ToggleFlag(x, y)`:
  - [ ] По закрытой клетке — поставить/снять флаг.
  - [ ] По открытой клетке — no-op.
- [ ] `StartNewGame()` и `StartNewGame(GameSettings)` — сброс состояния.
- [ ] `Elapsed` — через `TimeProvider`; стартует при первом открытии, останавливается при `Won`/`Lost`.
- [ ] `FlagsPlaced`, `MinesRemaining` — вычисляемые свойства.
- [ ] `RevealService` — каскадное открытие (итеративное, не рекурсивное, чтобы не ловить stack overflow на больших полях).
- [ ] `WinCondition` — проверка «все безопасные клетки открыты».

### Задачи — Events

- [ ] `CellChangedEventArgs` — `X`, `Y`, `CellState`, `CellContent`.
- [ ] `CellsRevealedEventArgs` — `IReadOnlyList<CellChange>`.
- [ ] `GameStateChangedEventArgs` — `OldState`, `NewState`.
- [ ] `BoardGeneratedEventArgs` — `GameSettings`.
- [ ] Подписка/поднятие в `GameEngine` строго по правилам из `04-AGENT-GUIDE.md`, раздел 4.

### Задачи — тесты

- [ ] `GameEngineTests`:
  - [ ] Первый клик никогда не мина (детерминированный `IRandomProvider` + `FakeTimeProvider`).
  - [ ] Открытие клетки с `N > 0` — открывается ровно одна клетка.
  - [ ] Открытие клетки с `N = 0` — каскад открывает ожидаемые клетки.
  - [ ] Каскад **не открывает** клетки с флагом.
  - [ ] Флаг блокирует прямой клик.
  - [ ] Поражение: все мины открыты, `GameState.Lost`.
  - [ ] Победа: все безопасные открыты, `GameState.Won`, оставшиеся мины (визуально) помечены.
  - [ ] `StartNewGame` сбрасывает состояние и флаги.
  - [ ] `Elapsed` стартует/останавливается в нужные моменты (через `FakeTimeProvider`).
- [ ] `EventTests`:
  - [ ] `CellChanged` поднимается один раз на одиночное открытие.
  - [ ] `CellsRevealed` поднимается один раз на каскад, не N раз.
  - [ ] `GameStateChanged` поднимается при переходах `NotStarted→InProgress`, `InProgress→Won/Lost`.

### Критерий готовности этапа

- [ ] Все тесты этапов 1–2 проходят.
- [ ] Core покрыт тестами по ключевым правилам (разделы 6–9 `GAME_RULES.md`).
- [ ] Архитектурный тест всё ещё проходит.
- [ ] Временная консольная «песочница» (не в репозитории, локально) позволяет сыграть партию, чтобы убедиться, что API удобно для UI.

### Риски и заметки

- **Каскад.** Рекурсия проста, но на больших полях (30×24, много нулей) может дать глубокий стек. Итеративная реализация с `Stack<Point>` или `Queue<Point>` — предпочтительнее.
- **«Флаг блокирует прямой клик, но не каскад».** Это правило (`GAME_RULES.md`, раздел 7) легко упустить. Тест обязателен.
- **События и реентрантность.** Если UI в обработчике `CellChanged` снова вызовет `OpenCell`, поведение должно быть предсказуемым. На MVP — не защищаться от этого, но зафиксировать в архитектуре, что Core не гарантирует реентрантность.

- **Ввод.** В MonoGame нет событий мыши — только polling. Детект клика: `current.LeftButton == Pressed && previous.LeftButton == Released`. Хранить `previousState` между кадрами.
- **Не тащить WinForms-код в MonoGame.** Общий только Core. Отрисовка и ввод — полностью разные.

Чтобы не было соблазна «расширить»:

- ❌ Сетевая игра, мультиплеер.
- ❌ Мобильные платформы (Android/iOS).
- ❌ Веб-версия (Blazor/WASM).
- ❌ Онлайн-таблица рекордов.
- ❌ Аккаунты, авторизация.
- ❌ Достижения, статистика, графики.
- ❌ Скины, темы оформления (кроме стандартного вида).
- ❌ Локализация (русский/английский) — на MVP только один язык, какой решит UI.
- ❌ Микрооптимизации Core (профилирование, span, SIMD и т.п.) — приоритет у ясности кода.

Если очень хочется что-то из этого списка — это **отдельный проект/форк**, а не расширение текущего roadmap.
