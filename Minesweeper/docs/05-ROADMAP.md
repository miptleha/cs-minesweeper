### Phase 7: WPF — ✅ Готово (0.4.0)

**Цель:** WPF — это «WinForms 2.0» от Microsoft. Та же экосистема
(MSBuild, Visual Studio), тот же C#, но декларативный XAML и MVVM. Агент знает
WPF очень хорошо: десятки тысяч примеров в обучающих данных. Начать с неё — значит
получить первый работающий UI за один-два прохода.

**Что осваивается:**

- XAML как декларативный язык разметки (vs императивный `Controls.Add(...)` в WinForms).
- Data Binding: `ItemsControl` с `UniformGrid` + `DataTemplate` для клетки.
- MVVM: `INotifyPropertyChanged`, команды, отделение логики от представления.
- `BitmapImage` + `Image` для ассетов; `EmbeddedResource` или `Resource` в `.csproj`.

**Зависимости.** Ничего скачивать не нужно — WPF входит в .NET SDK (`.NET Desktop
Development` workload, если ставили VS).

**Что переиспользуется из WinForms:**

- `JsonRecordStore` из `MinesweeperCore.Infrastructure` — общий JSON-файл рекордов.
- Логика ввода (Ctrl+ЛКМ → `CycleMark`) — та же, через `MouseUp`.
- Список ассетов — тот же (`assets/*.png` + `icon.ico`).

**Спецификация:** `docs/11-PHASE-7-WPF.md` — готова.

### Phase 8: Avalonia UI — ✅ Готово (0.5.0)

**Цель:** Синтаксис XAML почти идентичен WPF, поэтому порог входа
низкий. Это даёт **кросс-платформенность** (Windows / Linux / macOS) — важное
преимущество перед WinForms/WPF. Пакеты небольшие, `dotnet new avalonia.app`
поднимает проект за минуту.

**Что осваивается:**

- Кросс-платформенный XAML: те же Data Binding, `Styles`, `ControlTemplates`.
- Собственный рендерер Avalonia (SkiaSharp) — отличия от WPF в деталях
  (например, `Bitmap` vs `IImage`).
- Сборка self-contained и/или Native AOT (`-p:PublishAot=true`).

**Зависимости.** `Avalonia.Desktop`, `Avalonia.Themes.Fluent`, шаблоны
`Avalonia.Templates` — всё лёгкое.

**Что переиспользуется.** `GameEngine`, `JsonRecordStore`, `CellInfo`,
раскладка ввода (по `09` §6.1), те же ассеты.

**Спецификация:** `docs/12-PHASE-8-AVALONIA.md` — не создавалась, реализация выполнена без отдельной спецификации.

### Phase 9: Blazor Hybrid — ✅ Готово (0.6.0)

**Почему здесь.** Это смена парадигмы: HTML/CSS + компонентная модель C#.
Полезно для тех, кто хочет переносить навыки в веб. Blazor Hybrid в Windows
использует WebView2, который на Win11 уже установлен в 99% случаев.

**Ограничение (важно знать заранее).** При публикации self-contained
`.exe` **не включает** WebView2 Runtime — он внешний. На «чистой» машине
пользователя может потребоваться установка. Для учебного проекта и для себя —
не проблема; для дистрибутива «двойной клик — играем» — можно собрать установщик.

**Что осваивается:**

- Blazor-компоненты: `@code`, `[Parameter]`, `EventCallback`.
- Раскладка поля через HTML-`<table>` или CSS-grid.
- Взаимодействие C# ↔ DOM через `IJSRuntime` (минимально) и `@onclick`.
- Встраивание `GameEngine` как scoped-сервиса.

**Зависимости.** `Microsoft.AspNetCore.Components.WebView.WindowsForms` (или
WPF-версия). WebView2 Runtime — уже в Win11.

**Что переиспользуется.** Ядро, `JsonRecordStore`, ассеты (через `wwwroot/`
или прямо из `Resources/` через `RCL`), формы из WinForms UI.

**Спецификация:** `docs/13-PHASE-9-BLAZOR-HYBRID.md` — не создавалась, реализация выполнена без отдельной спецификации.

### Phase 10: Lumi (опционально) — ⬜ Запланировано

**Зачем.** Эксперимент: HTML/CSS как язык разметки, но рендеринг **нативный**
(SkiaSharp, без браузера). Это «лёгкий Blazor» без WebView2 — интересно
сравнить размер и скорость. Экосистема молодая, AI знает её хуже.

**Сложность.** 🟠 Средне-высокая — нужно разбираться с API, мало примеров.

**Нужна спецификация:** `docs/14-PHASE-10-LUMI.md` — только если решим делать.

---

### Phase 11: Duxel (опционально) — ⬜ Запланировано

**Зачем.** Immediate-mode GUI — это **другая парадигма**: никаких «виджетов»
и подписок на события, каждый кадр весь UI описывается заново по текущему
состоянию `GameEngine`. Максимальный контроль над отрисовкой, минимальный
оверхед, идеально для Native AOT. Это расширяет кругозор сильнее всего.

**Сложность.** 🔴 Высокая — мало обучающих данных, требуется понимать игровой
цикл и рисование.

**Нужна спецификация:** `docs/15-PHASE-11-DUXEL.md` — только если решим делать.

---

### Phase 12: MewUI (опционально, экспериментальная) — ⬜ Запланировано

**Зачем.** Показать, что GUI на .NET может быть **крошечным** (3–4 MB
self-contained exe) благодаря Native AOT. Чистый эксперимент, на грани
исследования.

**Сложность.** 🔴 Высокая — проект молодой и нестабильный. Может оказаться,
что его API сломается посреди разработки.

**Нужна спецификация:** `docs/16-PHASE-12-MEWUI.md` — только если решим делать.

## Общие требования ко всем новым UI-проектам

Чтобы ядро оставалось нетронутым, а версии — совместимыми между собой:

1. **Никаких изменений в `MinesweeperCore`.** UI только потребляет `GameEngine`,
   `CellInfo` и события. Если для UI нужны новые данные — это баг UI, не ядра.
2. **Общий `JsonRecordStore`** из `MinesweeperCore.Infrastructure` — единый
   `%LocalAppData%\Minesweeper\records.json` для всех версий. Рекорд,
   поставленный в WPF, виден в WinForms и наоборот.
3. **Общие ассеты** из `assets/` — копируются в проект по конвенции фреймворка
   (см. `04-AGENT-GUIDE.md`, раздел «Shared Assets»). Имена файлов не меняются.
4. **Раскладка ввода — по §6.1 `09-PHASE-5-WINFROMS.md`**: ЛКМ = `OpenCell`,
   ПКМ = `CycleMark`, Ctrl+ЛКМ = `CycleMark`,
   ЛКМ+ПКМ или средняя кнопка = `Chord`, клик по смайлику = `StartNewGame`.
   Поведение должно быть идентичным во всех UI.
5. **Смайлик и LED-счётчики** — визуально как в WinForms/MonoGame: `smiley_oh`
   при `MouseDown` на поле, `smiley_win`/`smiley_lose` по `GameStateChanged`,
   `minus.png` + две цифры при отрицательном `RemainingMines`.
6. **Каждый новый проект** добавляется в `Minesweeper.slnx` под `/src/`,
   `<ProjectReference>` на `MinesweeperCore.csproj`.
7. **Каждая фаза получает собственную спецификацию** `docs/NN-PHASE-M-TECH.md`
   по образцу `09`/`10`. Без спецификации реализацию не начинаем — иначе
   потеряется контракт с ядром.
8. **Release-конфигурация** — self-contained, `win-x64`, как в существующих
   проектах (`MinesweeperWinForms.csproj` / `MinesweeperMonoGame.csproj`).

## Дисклеймер

**Три обязательные фазы (WPF, Avalonia, Blazor Hybrid) выполнены** — релизы
0.4.0, 0.5.0 и 0.6.0. Оставшиеся три (Lumi, Duxel, MewUI) — опциональные
эксперименты: делать их не обязательно. После каждой фазы полезно ответить на вопросы:

- Что нового дала технология по сравнению с предыдущими?
- Насколько просто было интегрировать `GameEngine`?
- Есть ли что-то, что было бы удобнее в ядре, но ради чистоты архитектуры
  оставили как есть?

Эти ответы — главный результат эксперимента, а не количество готовых UI.
