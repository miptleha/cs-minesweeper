# 01 — Overview

## 🎯 Что это за проект

**CS-Minesweeper** — учебно-демонстрационный проект, реализующий классическую игру «Сапёр» (Minesweeper) на платформе .NET 8.

Главная цель проекта — **не просто написать игру, а продемонстрировать чистую архитектуру с разделением бизнес-логики и пользовательского интерфейса**, где одна и та же игровая логика используется несколькими независимыми UI-проектами, построенными на разных технологиях.

Проект задуман как «песочница» для изучения и сравнения подходов к созданию десктопных приложений и игр на C#.

## 💡 Ключевая идея: одно ядро — много интерфейсов

Вся игровая логика (правила, генерация поля, состояния, проверка победы/поражения) сосредоточена в **единственной библиотеке `MinesweeperCore`**, которая **ничего не знает о том, как игра отображается**.

UI-проекты — это «обёртки» вокруг ядра. Каждый из них реализует отрисовку, ввод и оформление по-своему, но использует один и тот же движок.

```

┌─────────────────────────────────────────────────┐
│                 MinesweeperCore                 │
│  (правила, модели, события, без UI-зависимостей)│
└─────────────────────────────────────────────────┘
      ▲             ▲             ▲             ▲
      │             │             │             │
┌─────┴─────┐ ┌─────┴─────┐ ┌─────┴─────┐ ┌─────┴─────┐
│  WinForms │ │  MonoGame │ │  Avalonia │ │    WPF    │
│  (primary)│ │ (planned) │ │  (future) │ │  (future) │
└───────────┘ └───────────┘ └───────────┘ └───────────┘
```

## 🧭 Цели проекта

### Образовательные

- Освоить **разделение слоёв** (domain / infrastructure / presentation) на практике, а не в теории.
- Понять, как писать **тестируемую бизнес-логику**, не зависящую от UI.
- Сравнить **разные UI-фреймворки** (.NET) на одной и той же задаче: WinForms, MonoGame, Avalonia, WPF.
- Разобраться с **событийной моделью** в C# и её ролью в слабой связанности компонентов.

### Практические

- Получить **рабочую игру «Сапёр»** с корректными правилами.
- Обеспечить **кроссплатформенность** хотя бы для одной из UI-реализаций (Avalonia или MonoGame).
- Сделать проект **удобным для AI-ассистентов** (GigaCode, Copilot и др.) через структурированную документацию.

### Не-цели (out of scope)

- Сетевая игра, рейтинги, аккаунты.
- Мобильные платформы (Android/iOS) — по крайней мере, на первом этапе.
- Сложная графика, шейдеры, 3D.
- Микрооптимизации и рекордная производительность — приоритет у ясности кода.

## 🎮 Кратко о правилах игры

Классический «Сапёр»:

- Поле из закрытых клеток. Часть клеток содержит **мины**.
- Игрок **открывает клетки** левым кликом. Если под клеткой мина — поражение.
- Открытая пустая клетка показывает **число соседних мин** (0–8). Если соседних мин нет — открывается каскад соседних клеток.
- Правый клик ставит/снимает **флаг** (предположение о мине).
- **Победа** — все безопасные клетки открыты, все мины помечены флагами (либо просто все безопасные открыты — см. спецификацию).

Полные и точные правила, включая пограничные случаи, — в **`02-GAME-RULES.md`**.

## 🚀 Текущий этап

**Этап 1: WinForms + Core (MVP).**

Задачи этапа:

1. Реализовать `MinesweeperCore` с нуля: модели, движок, события, генератор поля.
2. Реализовать `Minesweeper.WinForms` как основной UI: отрисовка поля, обработка мыши, таймер, счётчик мин, кнопка «Новая игра».
3. Покрыть ядро модульными тестами.
4. Убедиться, что Core не имеет UI-зависимостей.

Следующие этапы (см. `05-ROADMAP.md`):

- Этап 2: MonoGame-версия.
- Этап 3: Кроссплатформенная версия (Avalonia).
- Этап 4 (опционально): WPF.

## 🧩 Принципы разработки

- **Core не знает об UI.** Ноль ссылок на UI-библиотеки в проекте `MinesweeperCore`.
- **Направление зависимостей — всегда от UI к Core**, никогда наоборот.
- **События вместо прямых вызовов.** Core сообщает о том, *что* произошло (`CellChanged`, `GameStateChanged`), а не *как* это отрисовать.
- **Тестируемость.** Генерация поля и логика должны зависеть от абстракций (`IRandomProvider`), а не от `Random` напрямую.
- **Минимум магии.** Никаких «умных» фреймворков в Core — только чистый C# и BCL.
- **Ресурсы — в UI.** Картинки, шрифты, звуки живут в UI-проектах, а не в Core.
