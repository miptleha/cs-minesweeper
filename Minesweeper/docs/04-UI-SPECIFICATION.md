# 04 — Спецификация интерфейса

## Assets

В проекте лежат изображения необходимых картинок.
Файлы размещаются согласно конвенциям конкретного фреймворка.

| Файл | Назначение |
|---|---|
| `bomb.png` | Иконка мины (на открытой клетке с миной) |
| `cell_closed.png` | Закрытая клетка |
| `cell_empty.png` | Открытая пустая клетка (0 мин вокруг) |
| `cell_flag.png` | Клетка с флагом (накладывается на `cell_closed.png`) |
| `cell_question.png` | Клетка со знаком вопроса (накладывается на `cell_closed.png`) |
| `cell_wrong_flag.png` | Клетка с ошибочно поставленным флагом (при `Lost`) |
| `cell_exploded.png` | Клетка с миной, на которую кликнули (взрыв) |
| `digit_1.png` .. `digit_8.png` | Цифры для открытых клеток с N > 0 |
| `smiley.png` | Смайлик в нормальном состоянии (кнопка «Новая игра») |
| `smiley_oh.png` | Смайлик «о» — пока зажата левая кнопка мыши над полем (Board) |
| `smiley_win.png` | Смайлик в очках (победа) |
| `smiley_lose.png` | Смайлик с крестиками вместо глаз (поражение) |
| `minus.png` | Знак минус для счётчика мин (при отрицательных значениях) |
| `timer_0.png` .. `timer_9.png` | Цифры LED-счётчика (счётчик мин и таймер) |
| `icon.ico` | Иконка окна приложения |

В болванке проекта есть `Assets.cs`; если отсутствует — создать.  
Кэш предотвращает утечки памяти и повторное чтение ресурсов.
Картинки **не копируются** в папку с `.exe`, чтобы пользователь не мог их случайно удалить или испортить, а встраиваются в приложение (если это возможно).

## Архитектура UI

Запускаемое приложение, в котором можно сыграть полную партию:

- Поле рисуется текстурами.
- Все пути открытия/метки/аккорда работают по правилам `02-GAME-RULES.md`.
- Смайлик-кнопка показывает состояние: `smiley` / `smiley_oh` / `smiley_win` / `smiley_lose`.
- Счётчик мин и таймер обновляются в реальном времени, отрицательный счётчик
  рисуется через `minus.png`.
- Меню `Игра` / `Справка`, диалоги `Records` / `About` / `NamePrompt`.
- Сохранение рекордов — через `JsonRecordStore` из `MinesweeperCore.Infrastructure`
  (`%LocalAppData%\Minesweeper\records.json`).

### Окна и роли

В этом документе окна описываются по их **ролям**, а не по именам классов:

- **Main** — главное окно: отрисовка поля и игровой цикл;
- **Records** — окно таблицы рекордов (вкладки для уровней);
- **About** — окно «О программе»;
- **NamePrompt** — диалог ввода имени при установлении рекорда.

Имена в этом документе (`Main`, `Records`, `About`, `NamePrompt`) —
идентификаторы ролей, а не имена классов. Названия классов и типов окон
выбирайте по конвенциям целевого фреймворка: `Form` в WinForms,
`Window`/`ContentDialog` в WPF и Avalonia, `Window` в MAUI, `Popup`/`Dialog`
в ImGui и т. д. Нейтрализм документа важнее унификации имён:
обязательны только роль, поведение и содержимое окна, а не имя типа.

Для реализации окон необходимо использовать встроенные в UI-пакет классы окон,
если таких нет — использовать стандартное окно фреймворка.

Задача — показать компоненты конкретного UI-пакета, подключённого в проекте.

Меню, таблица результатов, кнопка со смайлом, панель с минами, расположение элементов —
для всего этого надо использовать встроенные в UI-пакет классы, если таких нет,
то использовать стандартные компоненты базового фреймворка.

В качестве эталона для содержимого окон можно взять проект MinesweeperWinForms.

### Main

Главное окно (`Main`) — **тонкий слой**. Вся игровая логика — в `GameEngine`. UI подписывается на события.
Скриншот главного окна (`game.png`) в корне, рядом с `README.md`.

```
┌──────────────────────────────────────┐ 
│ Игра  Справка                        │ ← Menu
├──────────────────────────────────────┤ 
│ [LED1]         [🙂]         [LED2]   │← TopPanel
├──────────────────────────────────────┤
│                                      │ ← Board
│                                      │
└──────────────────────────────────────┘
```

#### Меню

```
Игра
├── Новая игра          
├── ─────
├── Новичок             
├── Любитель            
├── Профессионал        
├── ─────
└── Выход

Справка
├── Лучшие результаты 
├── ─────
├── Управление             
├── ─────
└── О программе      
```

Используем меню из текущей UI-библиотеки или фреймворка, если такого нет, делаем сами красивое.

#### TopPanel

LED1 — **Счетчик мин**
LED2 — **Таймер**

LED-счётчики (см `02-GAME-RULES.md`).

**Счётчик мин:** `engine.RemainingMines = MineCount − флаги`.
- `>= 0`: 3 цифры
- `< 0`: `minus.png` + 2 цифры. Знак минуса занимает одну позицию.

**Таймер:** `Math.Min((int)engine.Elapsed.TotalSeconds, 999)`, 3 цифры.

#### Board

Поле (Board) сначала содержит закрытое поле 9x9 с 10 минами, на котором от кликов
отображаются картинки из списка Assets.
Правила отображения в `02-GAME-RULES.md`.

`Question` **не** считается флагом. При `Won`/`Lost` счётчик **не меняется** —
игрок своих действий не отменял.

**При `Won`**: ядро **не меняет** клетки. UI сам перерисовывает поле —
для каждой клетки, которая осталась `Closed` / `Flagged` / `Question`,
рисует `cell_flag.png` поверх. Это гарантированно мины (условие победы:
все безопасные уже `Opened`).

**При `Lost`**: триггерная клетка — `cell_exploded.png`; остальные
мины — `cell_empty.png` + `bomb.png`; `WrongFlag` — `cell_wrong_flag.png`.
Правильно помеченные мины остаются `Flagged` (награда за догадку), их
**не** открываем и **не** перерисовываем.

### Смайлик

Кнопка смайлика над полем. Клик по ней (в любом состоянии) — новая игра
(`StartNewGame` с текущими настройками).

Состояния:
- `smiley.png` — по умолчанию, в состоянии `NotStarted`/`Playing`;
- `smiley_oh.png` — пока зажата левая кнопка мыши над полем (Board):
  и над закрытыми клетками, и над открытыми цифрами (подготовка аккорда);
- `smiley_win.png` — при `Won`;
- `smiley_lose.png` — при `Lost`.

Правила `smiley_oh`:
- включается при зажатии ЛКМ в **любой точке поля (Board)**;
- НЕ включается при зажатии над меню, над TopPanel и за пределами окна;
- в состояниях `Won` и `Lost` не показывается никогда;
- сброс — при отпускании ЛКМ, при уходе курсора за пределы поля
  или при переходе игры в `Won`/`Lost` в момент зажатия.

### Управление

Месседжбокс с текстом при выборе из меню «Справка» → «Управление»:
```
ЛКМ — открыть клетку; повторный ЛКМ по открытой цифре — аккорд (открыть соседей).
ПКМ — метка: флаг → вопрос → пусто.
Ctrl+ЛКМ или долгое нажатие — то же, что ПКМ
```

### About

Содержит картинку бомбы, а справа от неё:

```
Сапёр <- крупный заголовок
Классическая игра «Сапёр».
Автор: miptleha.
```

Снизу текст-ссылка: "Скачать последнюю версию с GitHub" (https://github.com/miptleha/cs-minesweeper)

Кнопка `OK`, крестик в заголовке и `Esc` закрывают окно.

### Records

- TabPanel с тремя вкладками: `Новичок` / `Любитель` / `Профессионал`.
- В каждой — таблица с колонками `#`, `Имя`, `Время`.
Время с точностью до десятой секунды, после цифры текст "сек".
- Данные берутся из `IRecordStore.LoadRecords(level)`; пустое имя → `«Аноним»`.
- Крестик в заголовке и `Esc` закрывают окно.

### NamePrompt

Показывается только при победе на фиксированном уровне (не на Custom),
если время попало в топ-5.

- Label: Введите ваше имя:, TextBox: (по умолчанию `«Игрок»`),
  Button `OK` и `Cancel`.
- После `OK` — `PlayerName` из TextBox. Сохранить в рекорды:
    `RenameRecord(engine.Difficulty, engine.Elapsed.TotalSeconds, playerName)`
- Открыть диалог `Records`.

## Твой рабочий процесс (Workflow)

### Сценарий 1: Работа с Ядром (`MinesweeperCore`)

1.  **Архитектура:** Убедись, что используешь существующие порты (`IRandomProvider`, `IRecordStore`).
2.  **Код:** Пиши логику строго по `02-GAME-RULES.md`.

### Сценарий 2: Работа с UI

1.  **Инициализация:** Создай экземпляр `GameEngine`. Передай ему:
    - реализацию `IRandomProvider` — либо `SystemRandomProvider` из `MinesweeperCore` (тонкая обёртка над `System.Random`), либо свою;
    - реализацию `IRecordStore` — **обязательный** параметр (не опциональный). В `MinesweeperCore` есть `JsonRecordStore` — файловый.
2.  **Отрисовка:** В методе отрисовки запрашивай `CellInfo` для каждой клетки и рисуй соответствующую картинку.
3.  **Ввод:** Обработчик ввода маппится на ядро по правилам `02-GAME-RULES.md` (§6–§8):
    `OpenCell(point)` — ЛКМ по закрытой клетке; `Chord(point)` — ЛКМ по открытой цифре;
    `CycleMark(point)` — ПКМ (и её эквиваленты: Ctrl+ЛКМ, долгое нажатие).
4.  **События:** Подпишись на `CellChanged`, `CellsRevealed`, `GameStateChanged`. При их срабатывании обновляй состояние. **Не пиши логику игры в UI!**

## Важные дополнения

### Ассеты и ресемплинг
Исходные картинки — 64×64, на поле рисуются уменьшенными (24×24 при 100%).
Правила:
- при уменьшении запрещён nearest-neighbor — только качественный ресемплинг
  (bicubic, Lanczos; GDI+: `HighQualityBicubic`, SkiaSharp: `Medium`/`High`,
  ImageSharp: Lanczos3, MonoGame/FNA: преимпорт уменьшенных ассетов);
- результат кэшируется, ресемплинг не выполняется каждый кадр;
- пересчёт — только при смене масштаба.

### Системный масштаб (DPI)
Под масштабированием понимается ТОЛЬКО системный масштаб Windows
(Параметры экрана → Масштаб: 100–250%), а не опция в меню приложения.
- Базовая клетка — 24×24 при 96 DPI; фактический размер = 24 × DPI / 96.
  Панели, шрифты и размер окна пересчитываются пропорционально.
- Если фреймворк даёт событие смены DPI (WinForms `DpiChanged`, WPF, Avalonia,
  MAUI) — приложение обязано реагировать на лету, без перезапуска, включая
  перенос окна на монитор с другим масштабом (PerMonitorV2 в WinForms — без
  него события не будет).
- Если события нет (MonoGame/FNA/raylib, терминальные UI) — допускается
  фиксация масштаба при запуске; это указывается в фазе проекта.
- Не-DPI-aware приложение система растянет размытой картинкой — это дефект.
