# 04 — Спецификация интерфейса

## Статус проектов

UI-проекты в репозитории находятся в двух состояниях:

- **Готовые** — фазы 1–9 из `05-ROADMAP.md` (WinForms, MonoGame, WPF, Avalonia, Blazor Hybrid). Это полностью рабочие приложения; **их не трогать** — они служат эталоном поведения и содержимого окон.
- **Шаблоны** — заготовки с пустым главным окном и минимальной разметкой; их нужно наполнить по этому документу.

Все правила ниже применяются к шаблонам; готовые проекты им уже соответствуют.

## Assets

В проекте лежат изображения необходимых картинок.
Файлы размещаются согласно конвенциям конкретного фреймворка.

В шаблоне проекта есть `Assets.cs`; если отсутствует — создать.
Ассеты кэшируются: загружаются один раз и переиспользуются; чтение картинки из файла на каждый кадр недопустимо.
Картинки **не копируются** рядом с `.exe`, а встраиваются в приложение (если это возможно) — чтобы пользователь не мог их случайно удалить или испортить.

## Архитектура UI

Запускаемое приложение, в котором можно сыграть полную партию:

- Поле рисуется текстурами (для графических фреймворков; в терминальных UI — псевдографика, ассеты не используются).
- Все пути открытия/метки/аккорда работают по правилам `02-GAME-RULES.md`.
- Смайлик-кнопка показывает состояние: `smiley` / `smiley_oh` / `smiley_win` / `smiley_lose`.
- Счётчик мин и таймер обновляются в реальном времени, отрицательный счётчик
  рисуется через `minus.png`.
- Меню `Игра` / `Справка`, диалоги `Records` / `About` / `NamePrompt` (по возможности модальные — см. «Окна и роли»).
- Сохранение рекордов — через `JsonRecordStore` из `MinesweeperCore.Infrastructure`
  (`%LocalAppData%\Minesweeper\records.json`).

### Философия UI

- **Максимум встроенных классов.** Окна, меню, вкладки, таблицы, кнопки — из
  подключённого UI-пакета; если аналога нет — стандартные компоненты фреймворка.
  Свои компоненты — только когда без них никак. Цель каждой фазы — показать
  компоненты конкретного UI-пакета.
- **Идиоматичность фреймворка.** Пишем так, как принято в выбранном фреймворке
  (data binding и MVVM в WPF, события в WinForms и т. д.), а не переносим
  структуру WinForms-эталона в каждый проект. `MinesweeperWinForms` — эталон
  поведения и содержимого окон, но не организации кода.
- **Меньше кода — лучше.** Свои стили и кастомная отрисовка не нужны: используем
  стандартные компоненты и темы. Пиксель-в-пиксель соответствие скриншоту не
  является целью. Если библиотека рисует некрасиво — так и оставляем: это часть
  эксперимента, а не дефект.

### Окна и роли

В этом документе окна описываются по их **ролям**, а не по именам классов:

- **Main** — главное окно: отрисовка поля и игровой цикл;
- **Records** — окно таблицы рекордов (вкладки для уровней);
- **About** — окно «О программе»;
- **NamePrompt** — диалог ввода имени при установлении рекорда.

Имена в этом документе (`Main`, `Records`, `About`, `NamePrompt`) —
идентификаторы ролей, а не имена классов. Названия классов и типов окон
выбирайте по конвенциям целевого фреймворка: `Form` в WinForms,
`Window`/`ContentDialog` в WPF и Avalonia, `Window` в MAUI, `Popup`/`Dialog`
в ImGui и т. д. Обязательны роль, поведение и содержимое окна, а не имя типа.

Для реализации окон используйте встроенные в UI-пакет классы окон, если таких нет — стандартное окно фреймворка.

**Модальность.** Окна, открываемые из меню (`Records`, `About`, `NamePrompt`), делайте **модальными**, если фреймворк это поддерживает. Главное окно невелико: на уровне «Новичок» поле 9×9 занимает мало места, и окно «О программе» внутри него красиво не уместится. Содержимое этих окон не встраивайте в главное (панелями, «страницами», секциями) — это отдельные окна/диалоги. Если во фреймворке модальных окон нет (например, immediate-mode GUI) и нет базовых модальных окон — допустимо рисовать окно поверх главного средствами фреймворка.

В качестве эталона для содержимого окон можно взять проект MinesweeperWinForms.

### Main

Главное окно (`Main`) — **тонкий слой**. Вся игровая логика — в `GameEngine`, UI подписывается на события и рисует.
Скриншот главного окна для сверки смотри `game.png` в корне репозитория, рядом с `README.md`.

```
┌──────────────────────────────────────┐ 
│ Игра  Справка                        │ ← Menu
├──────────────────────────────────────┤ 
│ [LED1]         [🙂]         [LED2]   │← TopPanel
├──────────────────────────────────────┤
│                                      │ ← Board
│                                      │
└──────────────────────────────────────┘
```

#### Размер окна

- Размер окна подстраивается под поле: при смене уровня («Новичок» →
  «Любитель» → «Профессионал») окно расширяется или сужается до размеров
  меню + TopPanel + Board. TopPanel тянется на всю ширину окна; LED-экраны
  при этом разъезжаются к краям, смайлик остаётся по центру.
- Ручное изменение размера окна мышью запрещено. Кнопок максимизации и
  минимизации в заголовке нет; кнопка закрытия остаётся.

#### Размеры элементов

- Исходные картинки ассетов — 64×64 (правила ресемплинга — в разделе
  «Ассеты и ресемплинг»).
- Клетка поля — 24×24.
- Кнопка-смайлик — 32×32.
- LED-экран из трёх цифр — 72×32.
- Панели (меню, TopPanel) имеют внешние и внутренние отступы (margins/padding),
  поле (Board) — нет: клетки стыкуются вплотную. Если контейнер фреймворка
  добавляет свой отступ, его нужно обнулить — промежутки между клетками
  недопустимы.
- Базовые размеры заданы для 96 DPI и масштабируются вместе с системным
  масштабом (см. «Системный масштаб (DPI)»).


#### Меню

```
Игра
├── Новая игра          
├── ─────
├── Новичок             
├── Любитель            
├── Профессионал        
├── ─────
└── Выход

Справка
├── Лучшие результаты 
├── ─────
├── Управление             
├── ─────
└── О программе      
```

Меню берём из UI-пакета или фреймворка; если меню в нём нет — рисуем простое своё.

#### TopPanel

LED1 — **счётчик мин**; LED2 — **таймер**. LED-счётчики см. в `02-GAME-RULES.md`.

**Счётчик мин:** `engine.RemainingMines = MineCount − флаги`.
- `>= 0`: 3 цифры;
- `< 0`: `minus.png` + 2 цифры; знак минуса занимает одну позицию.

**Таймер:** `Math.Min((int)engine.Elapsed.TotalSeconds, 999)`, 3 цифры.

#### Board

При старте Board показывает закрытое поле 9×9 с 10 минами (уровень «Новичок»).
Дальше клетки перерисовываются ассетами из списка Assets по правилам
`02-GAME-RULES.md`. Клетки стыкуются вплотную, без отступов (см. «Размеры элементов»).

Знак вопроса (`Question`) не считается флагом и не уменьшает счётчик мин.
При `Won`/`Lost` счётчик не пересчитывается — остаётся таким, каким был
в момент конца игры.

**При `Won`** ядро клетки не меняет; UI сам дорисовывает поле: на каждую
клетку, оставшуюся `Closed` / `Flagged` / `Question`, поверх рисуется
`cell_flag.png` — это гарантированно мины (условие победы: все безопасные
клетки уже `Opened`).

**При `Lost`**: триггерная клетка — `cell_exploded.png`; остальные
мины — `cell_empty.png` + `bomb.png`; `WrongFlag` — `cell_wrong_flag.png`.
Правильно помеченные мины остаются `Flagged` (награда за догадку) — их
не открываем и не перерисовываем.

### Смайлик

Кнопка смайлика над полем. Клик по ней (в любом состоянии) — новая игра
(`StartNewGame` с текущими настройками).

Состояния:
- `smiley.png` — по умолчанию, в состоянии `NotStarted`/`Playing`;
- `smiley_oh.png` — пока зажата левая кнопка мыши над полем (Board):
  и над закрытыми клетками, и над открытыми цифрами (подготовка аккорда);
- `smiley_win.png` — при `Won`;
- `smiley_lose.png` — при `Lost`.

Правила `smiley_oh`:
- включается при зажатии ЛКМ в **любой точке поля (Board)**;
- НЕ включается при зажатии над меню, над TopPanel и за пределами окна;
- в состояниях `Won` и `Lost` не показывается никогда;
- сброс — при отпускании ЛКМ, при уходе курсора за пределы поля
  или при переходе игры в `Won`/`Lost` в момент зажатия.

### Управление

Диалоговое окно с текстом при выборе «Справка» → «Управление»:
```
ЛКМ — открыть клетку; повторный ЛКМ по открытой цифре — аккорд (открыть соседей).
ПКМ — метка: флаг → вопрос → пусто.
Ctrl+ЛКМ или долгое нажатие — то же, что ПКМ.
```

Все действия ввода (открытие, метка, аккорд) выполняются по **отпусканию** 
кнопки мыши — семантика `Click`/`MouseUp` в WinForms: нажал кнопку — это ещё не клик, 
клик засчитывается в момент отпускания.


### About

Содержит картинку бомбы в исходном размере 64×64 (без ресемплинга), а справа от неё:

```
Сапёр <- крупный заголовок
Классическая игра «Сапёр».
Автор: miptleha.
```

Снизу текст-ссылка: «Скачать последнюю версию с GitHub»
(https://github.com/miptleha/cs-minesweeper).

Кнопка `OK`, крестик в заголовке и `Esc` закрывают окно.

### Records

- Вкладки (таб-контрол по конвенции фреймворка):
  `Новичок` / `Любитель` / `Профессионал`.
- В каждой — таблица с колонками `#`, `Имя`, `Время`; время — с точностью
  до десятой доли секунды, после числа текст «сек».
- Данные — из `IRecordStore.LoadRecords(level)`; пустое имя отображается
  как `«Аноним»`.
- Крестик в заголовке и `Esc` закрывают окно.

### NamePrompt

Показывается только при победе на фиксированном уровне («Новичок»,
«Любитель», «Профессионал»), если время попало в топ-5.

- Label: «Введите ваше имя:», TextBox (по умолчанию `«Игрок»`),
  кнопки `OK` и `Cancel`.
- После `OK` — имя из TextBox сохраняется в рекорды:
  `RenameRecord(engine.Difficulty, engine.Elapsed.TotalSeconds, playerName)`.
- Затем открывается диалог `Records`.

## Рабочий процесс (Workflow)

### Ядро (`MinesweeperCore`)

- Используются существующие порты (`IRandomProvider`, `IRecordStore`); новые порты не создаются.
- Игровая логика пишется строго по `02-GAME-RULES.md`.

### UI

- UI создаёт `GameEngine`, передавая ему реализацию `IRandomProvider`
  (обычно `SystemRandomProvider` из `MinesweeperCore`) и реализацию
  `IRecordStore` — обязательный параметр (не опциональный); в
  `MinesweeperCore` есть файловый `JsonRecordStore`.
- В методе отрисовки UI запрашивает `CellInfo` для каждой клетки и рисует
  соответствующую картинку.
- Ввод маппируется в вызовы ядра по правилам `02-GAME-RULES.md` (§6–§8):
  `OpenCell(point)` — ЛКМ по закрытой клетке; `Chord(point)` — ЛКМ по
  открытой цифре; `CycleMark(point)` — ПКМ (и её эквиваленты: Ctrl+ЛКМ,
  долгое нажатие).
- UI подписывается на `CellChanged`, `CellsRevealed`, `GameStateChanged`
  и при их срабатывании обновляет экран.
- Игровая логика находится только в ядре: UI не дублирует правила игры
  (подсчёт мин, каскадное открытие, определение победы и поражения).

## Важные дополнения

### Ассеты и ресемплинг

Исходные картинки — 64×64, на поле рисуются уменьшенными (24×24 при 100%).
Правила:
- при уменьшении запрещён nearest-neighbor — только качественный ресемплинг
  (bicubic, Lanczos; GDI+: `HighQualityBicubic`, SkiaSharp: `Medium`/`High`,
  ImageSharp: Lanczos3, MonoGame/FNA: преимпорт уменьшенных ассетов);
- результат кэшируется, ресемплинг не выполняется каждый кадр;
- пересчёт — только при смене масштаба.

### Системный масштаб (DPI)

Под масштабированием понимается ТОЛЬКО системный масштаб Windows
(Параметры экрана → Масштаб: 100–250%), а не опция в меню приложения.
- Базовая клетка — 24×24 при 96 DPI; фактический размер = 24 × DPI / 96.
  Панели, шрифты и размер окна пересчитываются пропорционально.
- Если фреймворк даёт событие смены DPI (WinForms `DpiChanged`, WPF, Avalonia,
  MAUI) — приложение обязано реагировать на лету, без перезапуска.
- Если события нет (MonoGame/FNA/raylib, терминальные UI) — допускается
  фиксация масштаба при запуске; это указывается в фазе проекта.
- Не-DPI-aware приложение система растянет размытой картинкой — это дефект.
