# 07 — Testing Guide

## Принципы тестирования

1. **Только Ядро:** Тесты пишутся только для проекта `MinesweeperCore.Tests`. UI-проекты тестами не покрываются (для них пишутся интеграционные тесты или тестируется вручную).
2. **Изоляция:** Использование `System.Random`, `DateTime.Now`/`DateTime.UtcNow` или файловой системы в тестах запрещено. Используй фейковые реализации всех трёх портов: `IRandomProvider` (например, `FakeRandomProvider` с заданной последовательностью), `ITimeProvider` (например, `FakeTimeProvider` с ручным сдвигом часов), `IRecordStore` (например, `InMemoryRecordStore`).
3. **Поведение, а не реализация:** Тестируй публичное API ядра и игровые правила.
4. **AAA:** Arrange, Act, Assert.

## Случайность в тестах

Тесты используют `FakeRandomProvider` с фиксированным seed. Внутри фейка `new Random(seed)` — допустимо, потому что это фейк, а не ядро. Прямое использование `new Random()` без seed в тестах запрещено.

## Приоритеты покрытия

1. **Утилиты и модели:** Валидация границ `Board`, поиск соседей `CellPoint` (углы, края, центр).
2. **Безопасность:** Проверка, что первый клик всегда безопасен для
    кликнутой клетки (соседи могут содержать мины — классическое поведение).
    Проверка, что первый клик вне поля не запускает игру.
3. **Каскады:** Проверка, что Flood Fill открывает нужное количество клеток (итеративность, без StackOverflow).
4. **Состояния:** Переходы Win/Lose. Клик после окончания игры не меняет состояние.
5. **События:** Проверка, что UI получает корректные DTO (например, `CellsRevealed` вместо 50-ти `CellChanged`).

## Производительность

Тесты `PerformanceTests`:

- `Speed_30x24WithManyMines_RandomClicksUntilLost_Under1Second` — 30×24, 500 мин, случайные клики до `Lost`. Порог `1000` мс (включая `StartNewGame` и первый клик).
- `Speed_30x24WithFewMines_OpenAllSafeCellsUntilWon_Under1Second` — 30×24, 1 мина, открываем все безопасные клетки до `Won`. Порог `1000` мс.
- `Stress_1000x1000With100kMines_CreateAndFirstOpen_Under5Seconds` — 1000×1000, 100 000 мин. Порог `5000` мс. Замер включает `StartNewGame` + первый `OpenCell`.

Правила для тестов производительности:

1. Замер **включает** `StartNewGame` (создание `Board`) и первый `OpenCell`. Иначе «горячий» клик не проверит самую дорогую фазу.
2. Пороги с большим запасом: в `Release` `Stress_...` укладывается в ~0.05–0.1 с, в `Debug` — ~1–2 с (JIT + отсутствие инлайна на 1000×1000). Порог `5000` рассчитан на медленный CI.
3. `Stopwatch` в `PerformanceTests` — **исключение** из общего правила «не использовать `Stopwatch` в тестах». Ядро по-прежнему использует `ITimeProvider` (см. `08-CODE-CONSTRAINTS.md`).
4. `PerformanceTests` — не блокер для Phase 5, но отслеживает регрессии. Если падает — это повод смотреть код, а не поднимать порог.

## Границы `GameSettings`

`GameSettingsTests` покрывает валидацию:

- Принимает `(3, 3, 0)` .. `(1000, 1000, 0)` включительно.
- Принимает `MineCount` до `(Width−1)*(Height−1)`.
- Бросает `ArgumentOutOfRangeException` для `Width < 3`, `Height < 3`, `Width > 1000`, `Height > 1000`, `MineCount > (W−1)*(H−1)`.

## Тесты с ручной расстановкой мин

Для проверки `AdjacentMines` и каскадов используется `Board.PlaceMines(...)`:

```csharp
engine.BoardForTesting.PlaceMines(new[] { new CellPoint(8, 8) });
```

**Не** используйте `BoardForTesting.CellRef(x, y).IsMine = true` — это не обновляет `AdjacentMines` у соседей, и клетки вокруг мины откроются как `Empty` вместо `Number`.
