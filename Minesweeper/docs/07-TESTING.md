# 07 — Testing Guide

## Scope

Единый источник правил для агента при создании и изменении тестов
`MinesweeperCore`. Ссылка из `04-AGENT-GUIDE.md`.  

## Источник истины

- **Поведение** — `02-GAME-RULES.md`. Если тест противоречит GAME-RULES —
  это баг в коде, а не в тесте.
- **Порты и границы слоёв** — `03-ARCHITECTURE.md`.
- **Форма API** — существующий код в `src/MinesweeperCore/`.

Тест не должен повторять реализацию. Если тест можно «позеленить»,
поправив код на симметричную правку, — это плохой тест.  
Опора — `02-GAME-RULES.md`, а не «как написано в Board.cs».

## Фреймворк и раскладка

- xUnit (v2), `tests/MinesweeperCore.Tests/`.
- Папки повторяют `src/MinesweeperCore/`: `Domain/`, `Engine/`, `Events/`,
  `Records/`, `Abstractions/`.
- Файл: `<Class>Tests.cs`. Класс: `<Class>Tests`. Namespace:
  `MinesweeperCore.Tests.<Folder>`.
- Имя теста: `<Method>_<Scenario>_<Expected>`, например
  `OpenCell_FirstClickOnCorner_NeverHitsMine`.
- Один публичный класс ядра → один тестовый файл. Раздувать не надо —
  вспомогательные «сценарии» оформляй как private helper-методы в том же файле.

## Детерминизм — обязательно

Запрещено в тестах и в коде под тестом:
`Random`, `DateTime.Now`, `Guid.NewGuid()`, `File.*`, `Environment.*`,
`Task.Delay`, `Thread.Sleep`, сеть.
Любой такой источник в ядре уже должен быть за портом
(`IRandomProvider`, `IRecordStore`). В тестах — только фейки.

## Test doubles

- По умолчанию — **рукописные фейки** (Fake/Stub), лежат в
  `tests/MinesweeperCore.Tests/TestDoubles/`.
- `IRandomProvider` — скриптованный фейк: очередь заданных значений,
  `Next()` берёт следующее. Никакого seed-based `Random` — это flaky.
- `IRecordStore` — in-memory фейк (Dictionary/List), либо Moq **только**
  если проверяем факт/аргументы вызова `Save`/`Load`.
- Moq/NSubstitute не тянем, если хватает фейка.

## Стиль теста

- AAA (`Arrange / Act / Assert`) с комментариями-разделителями.
- Одна проверка одного поведения. Не «заодно ещё проверю три ветки».
- `[Theory]` + `[InlineData]` для матриц (углы/края/центр; размеры поля;
  все `DifficultyLevel`).
- События проверяем через подписку в `Arrange` и сохранение аргументов
  в локальную переменную; порядок событий — отдельный тест.
- Assert-библиотека — встроенная `Assert.*` из xUnit или Shouldly.
  FluentAssertions v8+ не используем (платная лицензия).

## Что тестируем

- Публичный контракт из GAME-RULES: правила открытия, флаги, победа,
  поражение, счётчики, переходы состояний, события.
- Границы: углы/края/центр, мин=0/макс, все пресеты, повторные вызовы
  (`OpenCell` на открытой, `ToggleFlag` на открытой), выход за границы поля.
- Инварианты: «первый клик всегда безопасен», «флагов ≤ мин»,
  «победа ⇔ все не-минные открыты».
- Внутренние сервисы (`MinePlacement`, `RevealService`, `WinCondition`) —
  тестируем напрямую, если у них есть публичный контракт, иначе через
  `GameEngine`.

## Что НЕ тестируем

- Приватные методы и внутренние поля.
- «Что код делает» вместо «что правило требует» — тест не должен повторять
  реализацию.
- 100% покрытие. Цель — покрытие **ветвлений правил** и публичного API.
- Фреймворк, BCL, сериализацию — это не наш код.

## Неоднозначность

Если GAME-RULES не описывают поведение:

1. Зафиксировать **текущее** поведение тестом с комментарием
   `// TODO: уточнить в 02-GAME-RULES`.
2. Не придумывать новое правило в тесте.
3. Если поведение очевидно должно быть другим — это баг в ядре, отдельная
   задача, а не «подгонка теста под код».

## Порядок покрытия (по возрастанию сложности)

1. `Point`, `Board`, `GameSettings`, `DifficultyPresets`, `RecordTable` —
   чистые, без портов.
2. `MinePlacement` — с фейком `IRandomProvider` (первый клик безопасен).
3. `WinCondition` — через `Board`.
4. `RevealService` — каскад (итеративность → нет StackOverflow на большом
   пустом поле), раскрытие мин при поражении.
5. `GameEngine` — состояния, счётчики, порядок событий, повторные вызовы.

## Проверка перед PR

- `dotnet test` — зелёный.
- Все новые публичные члены покрыты хотя бы одним позитивным и одним
  граничным тестом.
- Нет `Random`/`DateTime`/`File` в новом тестовом коде.
- Нет тестов, повторяющих реализацию (см. «Что НЕ тестируем»).
